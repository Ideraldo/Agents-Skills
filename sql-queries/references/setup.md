# Setting up the sql-queries skill

## One skill or several

Keep a single SQL skill with internal sections for SELECT and UPDATE:

- Some agents keep only one skill active at a time. A request that mixes both (a check SELECT inside an UPDATE script) would lose half the rules.
- The heavy context is the same in both cases: table schema and JSON formats. Two skills would duplicate it and drift apart.
- The rules that differ are few and fit in two short sections of the same file.

Split into another skill only for a genuinely different flow, such as writing ORM migrations, which has its own steps and checks.

## Folder layout

Everything lives in the service repository, in one folder, versioned with the code. Use the skills folder your agent reads (for example `.claude/skills/` for Claude Code or `.agents/skills/` for Devin).

```
sql-queries/
  SKILL.md
  json-examples.md
  schema/
    INDEX.md
    DatabaseA/
      dbo.Table1.Table.sql
      dbo.Table2.Table.sql
    DatabaseB/
      ...
```

| File | Contents | Maintained by |
|---|---|---|
| `SKILL.md` | The procedure: refine the request, T-SQL rules, response format | The team, via PR |
| `schema/<Database>/*.sql` | The CREATE TABLE of each table, one file per table | Generated by SSMS, updated with each migration |
| `schema/INDEX.md` | Database, table and a one-line description of the most used tables | Whoever knows the tables |
| `json-examples.md` | One sample JSON per JSON column, with fake values | Whoever knows the table |

Volume is not a problem: the agent doesn't read the whole folder. It checks the index, searches by table name and opens only what it needs.

**Before committing DDL, confirm with your team that the schema may be versioned in the repo.** If the agent platform doesn't support skills, put the SKILL.md content in a pinned knowledge item for the repository and keep the schema files in the repo.

## Step by step

1. **Create the skill folder** and paste `SKILL.md`.
2. **Generate the schema in SSMS.** For each database: right click > Tasks > Generate Scripts.
   - Choose Objects: "Select specific database objects", then Tables.
   - Set Scripting Options: "Save as script file" and "One script file per object", into a folder named after the database.
   - Advanced: "Types of data to script" = Schema only; Script Indexes and Script Foreign Keys = True.
3. **Copy into the skill** under `schema/<Database>/`.
4. **Write `schema/INDEX.md`** for the 10 to 20 tables the team uses most: database, table, one line on what it's for and which columns hold JSON. That business description is what no script can generate.
5. **Write `json-examples.md`** (see below).
6. **Test** with a real request and check that the agent delivers the understanding (stage 1) before the query.

## Alternative schema script

Use this when you want a compact tabular view, or in a client that can't generate DDL. It lists the tables of the connected database; switch with `USE DatabaseName;` and filter with the WHERE. It uses only standard SQL Server catalog views. If your user can't read `sys.foreign_key_columns`, remove that LEFT JOIN and the FK column.

```sql
SELECT
    c.TABLE_SCHEMA  AS [Schema],
    c.TABLE_NAME    AS [Table],
    c.COLUMN_NAME   AS [Column],
    c.DATA_TYPE
      + CASE
          WHEN c.CHARACTER_MAXIMUM_LENGTH IS NULL THEN ''
          WHEN c.CHARACTER_MAXIMUM_LENGTH = -1 THEN '(MAX)'
          ELSE '(' + CAST(c.CHARACTER_MAXIMUM_LENGTH AS varchar(10)) + ')'
        END         AS [Type],
    c.IS_NULLABLE   AS Nullable,
    CASE WHEN pk.COLUMN_NAME IS NULL THEN '' ELSE 'PK' END AS PK,
    ISNULL(fk.Reference, '') AS FK
FROM INFORMATION_SCHEMA.COLUMNS c
LEFT JOIN (
    SELECT ku.TABLE_SCHEMA, ku.TABLE_NAME, ku.COLUMN_NAME
    FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS tc
    JOIN INFORMATION_SCHEMA.KEY_COLUMN_USAGE ku
      ON ku.CONSTRAINT_NAME = tc.CONSTRAINT_NAME
     AND ku.TABLE_SCHEMA    = tc.TABLE_SCHEMA
    WHERE tc.CONSTRAINT_TYPE = 'PRIMARY KEY'
) pk
  ON pk.TABLE_SCHEMA = c.TABLE_SCHEMA
 AND pk.TABLE_NAME   = c.TABLE_NAME
 AND pk.COLUMN_NAME  = c.COLUMN_NAME
LEFT JOIN (
    SELECT
        OBJECT_SCHEMA_NAME(fkc.parent_object_id) AS TABLE_SCHEMA,
        OBJECT_NAME(fkc.parent_object_id)        AS TABLE_NAME,
        COL_NAME(fkc.parent_object_id, fkc.parent_column_id) AS COLUMN_NAME,
        OBJECT_NAME(fkc.referenced_object_id) + '.'
          + COL_NAME(fkc.referenced_object_id, fkc.referenced_column_id) AS Reference
    FROM sys.foreign_key_columns fkc
) fk
  ON fk.TABLE_SCHEMA = c.TABLE_SCHEMA
 AND fk.TABLE_NAME   = c.TABLE_NAME
 AND fk.COLUMN_NAME  = c.COLUMN_NAME
WHERE c.TABLE_NAME IN ('TableA', 'TableB')
ORDER BY c.TABLE_SCHEMA, c.TABLE_NAME, c.ORDINAL_POSITION;
```

To keep the schema from going stale: agree that every migration that changes a table also updates its file in `schema/` in the same PR.

## JSON examples

The schema only says a column is `NVARCHAR(MAX)`. Without an example the agent can't know what's inside, and that's where it invents fields. For each JSON column, record in `json-examples.md`:

- Table and column.
- A complete sample JSON, with the real structure and fake values.
- Which fields are optional and which are arrays.
- If the format changed over time, one example per version and when each applies.

To find candidate columns and grab a sample:

```sql
-- long text columns, candidates for JSON
SELECT TABLE_NAME, COLUMN_NAME
FROM INFORMATION_SCHEMA.COLUMNS
WHERE DATA_TYPE IN ('nvarchar', 'varchar')
  AND CHARACTER_MAXIMUM_LENGTH = -1
ORDER BY TABLE_NAME, COLUMN_NAME;

-- sample of one column (replace table and column)
SELECT TOP 3 JsonColumn
FROM TableA
WHERE ISJSON(JsonColumn) = 1;
```

Before saving an example, replace every real value with a fake one: names, documents, accounts, amounts. Keep keys, types and nesting, which is what the agent needs. **Customer data never goes into the repo or the prompt.**

## Skill, schema file or knowledge?

- If it has steps, it's the skill.
- If it's table structure, it's a schema file.
- If it's one sentence that prevents a mistake (a column that changed format, a status no longer used, what counts as an active record, "the agent has no database credentials here"), it's a pinned knowledge note.

## Is the context enough?

It's enough when most real requests come out usable on the first try. Measure instead of piling on rules.

- [ ] Pick 5 to 10 real requests: some SELECT, some UPDATE, at least two involving JSON
- [ ] Run them all with the skill and mark each: used as is, corrected, or discarded
- [ ] Run them again after every change to the skill and compare

How to read the result:

- A correction of a business rule only you knew: normal, good enough.
- An invented column or JSON field: missing schema or example.
- The same mistake twice: becomes one line in the skill or in knowledge.
- Rules being ignored: the SKILL.md got too long. Cut whatever wasn't born from a real mistake.

Start small: the rules in SKILL.md and the schema of 3 or 4 tables. Let repeated mistakes tell you what to add.
